# Independent quality evaluation

2026-11-25. The public YuE2 skill [evaluation instructions](https://github.com/multimodal-art-projection/YuE/blob/main/skills/yue2-music/references/listening-and-evaluation.md) do not ship the complete benchmark evaluator suite. Reuse individual public implementations without claiming equivalence to the exact WildSongBench run, decoder or selection protocol.

## Evaluator selection

- [Meta AudioBox Aesthetics](https://github.com/facebookresearch/audiobox-aesthetics) / [model card](https://huggingface.co/facebook/audiobox-aesthetics): CC BY 4.0 model and majority of code, with MIT portions. Approximately 100M parameters and 415 MB safetensors. Predicts content enjoyment (CE), usefulness (CU), production complexity (PC) and production quality (PQ). Default inference averages weighted 10-second 16 kHz mono windows. Not a stereo or full-song structure metric, not a pronunciation measurement. Complexity is not an optimization goal by itself.
- [ASLP-lab SongEval](https://github.com/ASLP-lab/SongEval): Apache-2.0 repository; five full-song scores for coherence, musicality, memorability, clarity and vocal breathing/phrasing naturalness. Uses noncommercial [MuQ-large-msd-iter](https://huggingface.co/OpenMuQ/MuQ-large-msd-iter) weights (~300M parameters), layer 6, 24 kHz mono, torch 2.7.0 and muq 0.1.0. Dataset includes English and Chinese songs, not evidence of calibrated Indonesian evaluation. Its CLI expects WAV/MP3 or a list, not direct FLAC. CPU path exists; full-song attention memory/time on 8 GB VRAM unverified.
- [Tencent SongBench](https://github.com/Tencent/SongBench) supports FLAC and seven separate song dimensions. [License](https://github.com/Tencent/SongBench/blob/main/LICENSE.txt) explicitly permits academic use only, not commercial or production use. Also depends on MuQ. Keep both SongEval and SongBench as optional research, not mandatory production dependencies. No approval to download them now.
- Native Whisper text disagreement remains a separate screen; do not present it as PER or a musicality score. Native timing and score checks remain separate evidence.

## AudioBox implementation

`audiobox-evaluate AUDIO_A.flac AUDIO_B.flac --weights LOCAL_MODEL.safetensors --out NEW_REPORT.json --confirm-evaluation` uses the upstream AesMultiOutput architecture and AesPredictor.forward, not a locally trained replacement. Overrides model setup to load verified local safetensors strictly, CPU only, with the public model config (F32). No remote model loader, pickle checkpoint, Studio call, new music, ASR or training. One full song per call, up to four distinct input files, each 1–360 s WAV/FLAC; ffprobe required. The upstream predictor batches 10-second windows within a song, so resource requirements still need real validation. Report gives separate CE/CU/PC/PQ values, file hashes and package versions; no ranking, acceptance threshold, release-ready claim or automatic regeneration. Do not publish private hashes or input files.

Model revision ce393651a6c9d61f62f8c3c68676229863a8a200, public SHA-256 a5a3c2412649cc2384ec525ffd5180ce6c4778f43bed6108e0a1303de04d014e. Config values recorded from the public HF config page. The actual wheel and checkpoint combination has not been executed or byte-compared in this environment.

## Optional installation and real acceptance

Use a separate Python 3.11 or 3.12 venv for optional torch dependencies; do not modify the user's existing Director Python runtime. Once reviewed and authorized, install pinned compatible CPU torch/torchaudio, requests, soundfile and the audited AudioBox package; verify availability/version and dependency lock before using it. Fetch only the single [pinned safetensors file](https://huggingface.co/facebook/audiobox-aesthetics/resolve/ce393651a6c9d61f62f8c3c68676229863a8a200/model.safetensors), verify the published SHA-256. No automated download in the command. If PyPI version is unavailable, audit and pin the actual upstream source commit rather than installing a moving branch. Keep optional weights and venv outside the repository. No training assets needed.

First actual evaluation should use retained existing takes (prefer the frozen B and finishing candidates if comparing a postprocessing effect). Do not generate another song to test installation. Compare score dimensions alongside existing ASR and acoustic evidence; no automatic acceptance or claim of significant improvement from tiny differences. Only after actual inference succeeds and repeatability/runtime are measured should it influence the Director decision policy.

Current evidence: on 2026-11-25, the operator successfully evaluated three retained whole-song mixes on Windows CPU using the pinned AudioBox model and the launcher. All four axes were returned. Differences in CE, CU and PQ were below 0.01 score units; PC differed slightly more. This single comparison does not establish repeatability, significance, musical improvement or phonetic accuracy. Do not repeat the completed evaluation merely to test a launcher. Custom dynamics remains experimental, not a default; prefer native workflows when they meet the goal.

## Windows import troubleshooting

The first local setup installed AudioBox 0.0.4, CPU torch/torchaudio 2.7.1 and soundfile, and passed the checkpoint guard, but failed at imports. Upstream `utils.py` imports `requests` unconditionally while its `pyproject.toml` does not declare requests. The package was not listed in the local installation log; installing requests resolved the import failure in the actual local environment. In the existing isolated evaluator venv run `python -m pip install requests`, then `python -c "import torch, torchaudio, requests; from audiobox_aesthetics.infer import AesPredictor; from audiobox_aesthetics.model.aes import AesMultiOutput, Normalize; print('AudioBox imports OK')"`. Do not reinstall torch or redownload verified weights. The command now reports the original ImportError class and message for any remaining dependency mismatch. No inference succeeded in the failed attempt.

## Windows one-command retained evaluation

After the initial isolated evaluator installation, run `eval.cmd` from the repository (or double-click the file in Explorer). The launcher uses the sibling yue2-eval-cpu environment and resolves its repository directory from its own path, regardless of the current directory. It does not reinstall dependencies or download a checkpoint. It finds a unique completed custom/native-headroom pair using matching local report fingerprints, verifies candidate bytes, reuses any matching saved evaluation, or resolves the original through the read-only Studio library endpoint and verifies source bytes before CPU evaluation. The launcher explicitly defaults to loopback port 8791; override with YUE2_MCP_URL if needed. Studio must be running with its MCP enabled for a new evaluation. A saved matching result requires no Studio connection. Model loading and per-file inference progress are printed; errors preserve exception details. No generation or recognition. Do not start the launcher while another manually started evaluation is still running. If multiple comparisons exist, the launcher stops instead of guessing. The lock protects only launcher invocations, not older direct CLI invocations. No private input paths or IDs are committed. Real CPU inference succeeded in the retained comparison.

## Cross-device test handoff

The Windows PC and chat device may be separate. Do not require copying terminal output or manually retyping multiline commands. Run checked-in launchers and attach the local TXT report. `eval.cmd` streams console output and writes stdout, stderr and exit code to `results/eval-output.txt` (latest invocation). The transcript is local and may contain private diagnostic paths; never commit it. The existing JSON result remains the authoritative saved scores and is reused on subsequent calls. Do not rerun the evaluator just to test the transcript writer. Future Windows test launchers should reuse the logged_command helper where appropriate.
